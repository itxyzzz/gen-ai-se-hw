## Goal

Create the Homework 6 Hephaestus (Code Generator) automation control surface so a later Homework 6-root run can consume the selected `specification.md`, use Context7 during code generation, and produce the generated Python transaction-processing pipeline without mixing operator harness rules into the generated product.

## Scope

- Add a tool-neutral Hephaestus (Code Generator) control package under `homework-6/agent-control/generate-code/`.
- Add Codex and Claude Code entrypoint wrappers for the code-generation automation agent.
- Define the Hephaestus workflow for reading the selected Athena (Spec Writer) output, using Context7 MCP for stack/framework lookups, preserving generation evidence, generating product code into canonical Homework 6 files, and documenting Context7 usage in canonical `research-notes.md`.
- Define Hephaestus executor sub-agent autonomy: the later code-generation run may spawn bounded executor sub-agents up to the Homework 6 `agents.max_threads = 8` configuration without asking for additional operator approval, with one sub-agent per selected-spec task or implementation slice preferred when it improves quality.
- Define run-preservation rules for Hephaestus (Code Generator) attempts under `homework-6/docs/agent-runs/`.
- Add quality gates that keep Hephaestus focused on Task 2 generated transaction-system code and prevent it from implementing Task 3, Task 4 custom MCP server/config expansion, Task 5 documentation, screenshots, or PR packaging.
- Update the standing Homework 6 agent guide only where it needs to point to the Hephaestus control surface and clarify the boundary between the automation agent and runtime transaction pipeline components.

## Non-scope

- Do not invoke Hephaestus (Code Generator) to generate the transaction-processing pipeline in this work item.
- Do not create `integrator.py`, runtime `agents/`, runtime `tests/`, `shared/`, generated `research-notes.md`, generated `README.md`, generated `HOWTORUN.md`, generated screenshots, or other Generated Transaction System Layer outputs in this work item.
- Do not add the custom `pipeline-status` MCP server, `mcp/server.py`, or `pipeline-status` entries to `mcp.json` or `.codex/config.toml`; those remain later Task 4/generated-system work after result shapes exist.
- Do not edit the selected generated product specification except to read it as context for Hephaestus workflow design.
- Do not change the frozen assignment file `homework-6/TASKS.md`.
- Do not make runtime transaction pipeline components use Greek labels such as Hephaestus, Athena, Themis, or Clio.

## Proposed behavior

Add a Hephaestus (Code Generator) automation package that can be invoked later from a project rooted at `homework-6`. The package should mirror Athena's durable shape but adapt it for code generation:

```text
homework-6/agent-control/generate-code/
  README.md
  workflow.md
  quality-bar.md
  run-registry.md
```

Add thin wrappers:

```text
homework-6/.agents/skills/generate-code/SKILL.md
homework-6/.claude/skills/generate-code/SKILL.md
```

The wrappers should instruct the runtime to read and follow the shared package. The shared package should define modes such as `generate`, `resume`, and `compare`, with `generate` as the default. A normal Hephaestus run should:

1. Load `homework-6/specification.md`, `homework-6/agents.md`, `homework-6/sample-transactions.json`, Homework 6 task requirements, root repository standards when available, and the Hephaestus control references.
2. Confirm the selected stack from the spec, currently Python.
3. Verify Context7 is configured or record a clear limitation if MCP access is unavailable.
4. Use Context7 during code generation for at least two concrete Python implementation questions, such as Decimal monetary handling, pytest/coverage usage, JSON/file handling, argparse CLI behavior, pathlib/shutil filesystem operations, or FastMCP only if the generated code reaches MCP-readable result helper design.
5. Preserve the search text, returned library ID, access date, and applied insight for each Context7 query in canonical `homework-6/research-notes.md`.
6. Generate Task 2 product code only: integrator/orchestrator, runtime transaction pipeline components, shared JSON protocol handling, result summaries, and unit/integration seams expected by the selected spec.
7. Use executor sub-agents freely within the configured Homework 6 cap of eight active threads when the runtime supports them. The preferred pattern is one bounded sub-agent per selected `specification.md` low-level task or per independently testable implementation slice, in waves when more than eight slices exist. The orchestrator may choose fewer sub-agents when a task is tightly coupled, requires one integration owner, or parallelism would degrade quality.
8. Shape each sub-agent with curated context and a deliberate model/reasoning choice. The workflow may borrow the context-strategy and policy-relative model-selection vocabulary from `dev-doc-harness` `subagent-model-policy.md`, but it must copy the needed guidance into the Hephaestus package rather than requiring the later Homework Automation Layer run to load the harness.
9. Treat the approved Hephaestus workflow as authorization for planned sub-agent use within the config cap. Hephaestus must not ask the operator for another sub-agent-specific approval merely because the later start prompt does not repeat the word `sub-agent`.
10. Avoid implementing Task 3 skills/hooks, Task 4 custom MCP server/config additions, Task 5 final docs, screenshots, or PR packaging.
11. Preserve run evidence under a new Hephaestus run folder in `homework-6/docs/agent-runs/`.
12. Validate with stack-appropriate commands such as `python integrator.py` and focused pytest checks when tests are included by the selected spec or generated alongside the pipeline.

Hephaestus should write generated product files directly to the canonical Homework 6 product paths only during a later authorized generation run. The control-surface implementation planned here only creates the automation instructions that make that later run safe and repeatable.

## Risks

- The Hephaestus workflow could accidentally generate Task 3, Task 4, or Task 5 deliverables too early. Mitigation: make Task 2 scope explicit and add quality-bar rejection checks for hooks, command skills, custom MCP server/config expansion, screenshots, README/HOWTORUN, and PR packaging.
- The control surface could depend on Codex-only or Claude-only behavior. Mitigation: keep wrappers thin and put canonical behavior in `agent-control/generate-code/`.
- Context7 could be unavailable in a later run despite configuration being present. Mitigation: require the run to record the limitation in `research-notes.md` and in the preserved run metadata, then continue only if the operator accepts the degraded mode or the assignment can still be satisfied by a separate Context7-enabled run.
- Excessive or poorly shaped sub-agent fan-out could lower generated-code quality through inconsistent assumptions, duplicated edits, or weak integration. Mitigation: make the orchestrator the final integration owner, prefer curated context over full-history forks, require sub-agent reports, run sub-agents in waves within the `agents.max_threads = 8` cap, and allow the orchestrator to choose fewer sub-agents when parallelism would hurt quality.
- Hephaestus could leak operator harness concepts into generated transaction-system files. Mitigation: reuse the layer glossary and explicitly ban `dev-doc-harness`, freeze gates, run-preservation mechanics, and Greek automation labels from generated runtime product code.
- Generated code could expose sensitive sample fields in logs or results. Mitigation: make privacy/audit checks first-class in the code-generation quality bar.
- Future code generation could overwrite valuable user changes. Mitigation: require preflight git status, diff review, and explicit handling of existing product files before writing canonical generated outputs.

## Acceptance criteria

- A new `agent-control/generate-code/` package exists with README, workflow, quality bar, and run registry.
- Codex and Claude Code `generate-code` entrypoints exist and are thin wrappers around the shared Hephaestus package.
- `homework-6/agents.md` references Hephaestus (Code Generator)'s new control surface without changing the layer model or applying Greek labels to runtime pipeline components.
- The workflow requires Hephaestus to consume the selected `homework-6/specification.md` and preserve code-generation run evidence under `homework-6/docs/agent-runs/`.
- The workflow requires Context7 use during generation and requires at least two documented query entries in canonical `homework-6/research-notes.md` with search text, returned library ID, access date, and applied insight.
- The workflow authorizes Hephaestus to spawn executor sub-agents without additional operator approval up to Homework 6's configured `agents.max_threads = 8` cap, preferably one per selected-spec task or implementation slice when quality benefits.
- The workflow requires curated sub-agent context, deliberate policy-relative model/reasoning selection, sub-agent reports, and orchestration-thread final integration ownership.
- The quality bar limits a normal Hephaestus run to Task 2 generated transaction-system code and rejects premature Task 3 skills/hooks, Task 4 custom MCP server/config additions, Task 5 docs/screenshots, and PR packaging.
- The quality bar requires generated code to follow the selected spec's privacy, Decimal money, JSON protocol, deterministic result, and validation expectations.
- `homework-6/TASKS.md`, `homework-6/specification.md`, `homework-6/mcp.json`, and `homework-6/.codex/config.toml` are unchanged by this control-surface implementation unless a later approved variance explicitly changes them.
- `homework-6/CHANGELOG.md` records the Hephaestus planning and implementation increments before commits.
